# Випуск 5.12.0: захист акаунтів і контроль даних

Цей випуск зберігає чинні адреси, показники, історію оплат, тарифи, нагадування, постачальників, гостьові посилання та локальні чернетки. `ACCOUNT_STORE`, KV Namespace ID `d16e9ce7ed3e4e688f1d19b33c26c13d`, Firebase project і протокол синхронізації не змінюються.

## Що змінилося

- Нові акаунти створюються окремою дією, а паролі зберігаються як salted PBKDF2-SHA256 verifier.
- Під час першого успішного входу старого акаунта його SHA-256 формат автоматично мігрує у verifier; записи й налаштування залишаються без змін.
- Після входу використовується короткий opaque session token. Зміна пароля відкликає всі старі сесії й видає поточному пристрою нову.
- У профілі доступні створення/зміна пароля, експорт без секретів, керування гостьовими посиланнями й повне видалення акаунта з підтвердженням.
- Адмінське скидання пароля використовує той самий сильний verifier і завершує сесії користувача. Секрети не повертаються адмінському UI.
- Rate limit і голосування/модерація спільних тарифів серіалізовані Durable Object, тому паралельні запити не гублять стан.
- Landing більше не запускає сторонній Tailwind runtime; CSP, HSTS і локальні vendor-ресурси узгоджені.
- Обмеження масштабу у viewport `index.html` навмисно залишене без змін на прохання власника.

## Перед production

1. Зробити приватний raw backup KV і перевірити JSON, кількість ключів та SHA-256. Для міграції використовувати повний експорт із адмінпанелі: саме він містить `manifest`, акаунти й raw KV entries та проходить `npm run backup:verify -- /absolute/path/backup.json --for-migration` у read-only режимі.
2. Розгорнути Worker із тим самим KV binding і Durable Object, виконати `npm run worker:check`.
3. Перевірити health, вхід старим акаунтом, нову реєстрацію, зміну пароля, Telegram/Push і гостьове посилання на окремому тестовому акаунті.
4. Опублікувати frontend після Worker. Перший вхід кожного старого акаунта виконує сумісну міграцію лише після перевірки правильного пароля.

Відкат frontend не видаляє дані. Після першої password migration старий frontend, який очікує SHA-256 bearer, уже не зможе автентифікувати цей акаунт; у такому випадку повертають сумісний Worker або завершують контрольований випуск, не перезаписуючи KV навмання.
